- **`오프셋 기반 페이지네이션`**과 **`커서 기반 페이지네이션`**에 대해 정리해보세요! 🍠
  - `오프셋 기반 페이지네이션`의 장/단점 (`offset-based pagination`) 🍠
    - `오프셋 기반 페이지네이션`은 무엇인가요? 🍠
      - `LIMIT`과 `OFFSET` SQL 쿼리를 사용하여 데이터를 나눠서 가져오는 방식
      ```sql
      SELECT * FROM posts ORDER BY created_at DESC LIMIT 10 OFFSET 20;
      ```
      - 보통 `?page=3&limit=10` 이런 형태로 사용됨.
    - `오프셋 기반 페이지네이션`의 장점? 🍠
      1. 구현이 쉽다.
         - SQL에서 바로 지원하고 프론트와 백엔드 모두 작성하기 간단하다.
      2. 임의 페이지 접근이 쉽다.
         - 사용자가 원하는 페이지(예: 5페이지)로 쉽게 이동이 가능하다.
      3. 정렬과 무관하다.
         - 다양한 필드로 정렬해도 OFFSET/LIMIT 방식은 그대로 사용 가능하다.
    - `오프셋 기반 페이지네이션`의 단점? 🍠
      1. 성능이 저하된다.
         - `OFFSET`이 클수록 DB는 더 많은 데이터를 스캔 후 버림 ⇒ 느려짐
      2. 데이터 중복의 위험과 누락의 위험이 있다.
         - 실시간 데이터 변경이 있는 경우 순서가 바뀌어 중복 또는 누락 발생의 가능성이 있다.
      3. 무한 스크롤에 부적합하다.
         - 빠른 연속 요청에 부정확한 위치를 반환할 수 있다.
  - `커서 기반 페이지네이션`의 장/단점 (`cursor-based pagination`) 🍠
    - `커서 기반 페이지네이션`은 무엇인가요? 🍠
      - 각 데이터 항목의 고유한 식별자(`id`, `createdAt` 등)를 기준으로 이후 데이터를 조회하는 방식
      ```sql

      SELECT * FROM posts WHERE id < 'last_seen_id' ORDER BY id DESC LIMIT 10;
      ```
      - 주로 `?cursor=last_seen_id&limit=10` 형태로 사용
    - `커서 기반 페이지네이션`의 장점 🍠
      1. 성능이 우수하다.
         - 특정 위치부터 바로 가져오기 때문에 OFFSET보다 훨씬 빠르다.
      2. 일관된 결과를 보인다.
         - 데이터 중간에 삽입/삭제가 있어도 중복 없이 정확한 순서를 유지한다.
      3. 무한 스크롤에 적합하다.
    - `커서 기반 페이지네이션`의 단점 🍠
      1. 구현이 복잡하다.
         - 커서 관리 및 정렬 방향에 따라 쿼리 조정이 필요하다.
      2. 특정 페이지에 접근이 불가하다.
         - 5페이지로 바로 이동 같은 기능이 어렵거나 불가능하다. ( 페이지 개념이 없기 때문 )
      3. 정렬 기준에 제한이 있다.
         - 커서로 사용하는 필드는 정렬 기준과 일치해야 한다.
